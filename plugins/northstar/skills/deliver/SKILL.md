# deliver —— 交付核验（独立入口）

把目标态从"在我这里成立"变成"在需求者那里成立"，并核验**交付物 = 契约声明的需求与交付结果**。

回路终点不是"代码正确"，是"改动生效"。实施完成与交付达成之间隔着一整类失败：产物没送出去、送到了但消费端取的是旧版本、生效了但与契约声明的形态不符——这些失败**没有任何回路节点会发现**，因为回路各相都只看自己这侧。

## 触发与前置

**口头独立触发**（发版 / 交付 / 上线 / 部署），**不挂任何回路节点**——交付频率与回路节奏天然不对齐：一次交付可含多轮实施，一轮实施也可能永不单独交付。

前置：本轮实施与收尾链已走完。未走完不交付——把未过质量刀的改动送出去，等于把回路的门开在身后。

## 机制：主会话执行，不派子代理

本相**不派子代理**——纪律一要求向人确认不可逆动作，而子代理没有向人确认的通道。这与 audit / code-review / simplify 的硬性派发相反：那三处要的是独立性，本相要的是**人的授权**。

## 三标准（形态无关，机械可判定）

1. **交付形态入契约**：契约须声明交付形态——产物是什么、落到哪里、消费者怎么取用、版本如何标识。**契约未声明 = 契约缺口 → 回踢 brainstorming**，本相不臆断形态、不替契约做主。
2. **从消费端取证，不从生产端**：判据取自**消费者实际取到的东西**，不取自生产端的成功回执。"推送成功""构建通过""命令没报错"都是生产端信号，它们与"消费者拿到了新版本"之间可以任意脱节。取证须站在消费者的位置实际取一次。
3. **一致性锚定版本**：取证须锚定明确的版本标识，并与本次交付的版本逐一比对。没有版本锚的取证不成立——"看起来是新的"不是判据。

核验项按**验证清单规格**书写（每条有判定命令或可观察证据，答案非"是"即"否"；规格见 `write-test` 的「验证清单规格」节，此处不复述）。

## 三纪律

1. **不可逆动作需人 Gate**：发布、推送、迁移、覆盖、通知外部——凡不可撤销者，执行前呈请人确认，说明将做什么、影响面、可否回退。人未确认不执行。
2. **验证发生在发布之后**：发布前的检查是准备，不是验证。真正的验证只能在产物于消费端可取用之后做——顺序不可颠倒，颠倒了就只是在验证自己的意图。
3. **交付契约是持续契约**：交付形态一旦声明进契约即持续有效，后续轮次不得静默破坏它（改了交付形态而不改契约 = 契约漂移，按契约缺口回踢）。

## 流程

1. **取契约的交付形态声明**——缺失 / 含糊 → 回踢 brainstorming，本轮止。
2. **备物**：生成或更新交付物，推进版本标识（版本不动 = 消费端可能按版本比对而静默拒收，这是真实失败模式，不是理论风险）。
3. **人 Gate**：呈请确认不可逆动作。
4. **执行交付**。
5. **消费端取证**：站在消费者位置实际取一次，锚定版本比对，逐条过核验清单。
6. **判决**：全部核验项为"是" → 交付达成；任一为"否" → 按下节分流。

## 出口

- **交付达成**：记录本次交付的版本锚与取证结果（过程态出境）。
- **契约缺口**（形态未声明 / 声明与现实不符）→ **brainstorming**。
- **交付失败且因不明** → **diagnose** 归因，按其出口分流。
- **交付失败且因明确在实现** → **implement** 修，修完重走本相（不得跳过重新取证）。

**收敛阀**：同一交付缺口反复触发达阈值（默认 3 次）仍不收敛 → BLOCKED 升级给人，附回踢历史（过程态出境）。

## 不变量

1. **契约只读**：本相不写 README。发现缺口回踢，不自补。
2. **不静默降级**：取不到证据 ≠ 交付成功。消费端取证失败时不得以生产端信号替代，也不得以"应该没问题"结案。
3. **过程态出境**：交付记录、踩坑、版本历史一律出境，不入契约。
4. **范围止于交付**：产物是否可取用、是否与契约一致——到此为止。运行期的可观测性、事故响应、性能调优与回滚编排**不属本相**，那是运行期工具的地盘。

---
来源：northstar 自著。三标准与三纪律出自 2026-08 实证——一次"改完契约以为生效了，实际运行时加载的仍是安装缓存里的旧版本、全程无提示"的真实失败，以及随后发版实测中"内容变更未推进版本标识则更新被静默拒绝"的复现。
