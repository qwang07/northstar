# code-review —— 仅质量的独立评审（吸收自 superpowers，自著薄版）

收尾链末道：`simplify` 精简之后、合并之前（simplify 的适用范围按代码判，判据见该 skill；本轮无代码在其 scope 内时，直接从 implement 来）。**只补"代码质量"那一刀**，不重复已有的关卡。

## 边界（不重复造轮子）
- **契约合规**（实现是否恰好 = 模块契约、有无多做/少做）→ 归 implement 退出门，本 skill 不碰。
- **设计完整度 / 契约↔测试一致** → 归 audit，本 skill 不碰。
- 本 skill 只查**契约与测试都表达不了的代码质量**：潜在 bug、错误路径与静默失败、可维护性、边界。
- **已声明的安全约束**：横切层声明了才查（见检查清单「安全」项）。与上两条不冲突——契约合规门查"功能是否恰好等于契约"，本项查"代码在错误路径与边缘上是否泄漏 / 越权"；后者难以穷举测试，正落在"测试表达不了"的那一格。

## 机制：零上下文子代理（同 audit 一脉）
派零上下文子代理评审——输入**仅** git diff（BASE..HEAD）+ **模块 README 契约**（作为规格）+ **本轮守护物**（测试文件；免测试分支给验证清单）+ 一句改动描述；**不给 session 历史、不补背景**（同 audit 的 dispatch 红线，防 controller 善意泄漏把上下文偷渡进去）。
**守护物为何必须在场**：本 skill 有一条审项是"契约与测试**未覆盖**路径上的缺陷"——拿不到守护物就判不出什么已被覆盖，该审项当场不可执行。守护物只作**覆盖面参照**，不作规格：规格恒为模块 README（守护物本身若与契约不符，那是 audit 的领地，不在此裁）。
**只读 checkout**：评审不得动 working tree / index / HEAD；要看别的版本就 `git worktree` 到临时目录，绝不在本 checkout 上挪 HEAD。
**派发声明**：工具面 = 只读 · 推理档位 = 判断类高档。（只读如何兑现与核验见项目 README「跨平台拓扑·横切约束」；档位如何落成调用参数见平台执行说明，此处均不复述。）

## 检查清单（锚定模块 README 契约）
- **契约偏离**：实现是否偏离模块 README？只**标记偏离让人确认**，不在此裁决——裁决是 implement 门的事。
- **错误路径 / 静默失败**：吞异常、空 catch、错误未 surface/log、不当 fallback —— 零容忍（吸收自 silent-failure-hunter）。
- **潜在 bug**：契约/测试未覆盖路径上的真实缺陷。聚焦大问题，避开 linter/类型器能抓的琐碎与假阳性。
- **可维护性**：职责分离、类型安全、DRY 而不过度抽象、边界情况是否处理。
- **安全**（**仅当**契约的横切层声明了安全约束时启用；通则见项目 README「非功能约束同走声明→派生→审查」，此处不复述）：注入（查询 / 命令 / 模板 / 路径拼接是否参数化或转义）· 认证与授权（缺失、越权、水平 / 垂直提权）· 凭据与秘密（硬编码、日志与错误信息泄漏）· 不可信输入的反序列化 · 路径穿越 · 服务端请求伪造 · 敏感数据在传输与静态存储的处理。**未声明则不查**——不声明就不做，与测试范围铁律同源。

## northstar 不变量
1. **发现只读**：评审发现对 implement 循环只读——按边界二处理（满足它，或判定为契约缺陷而回踢 brainstorming 补契约），**不得软化、不得预判**。
2. **不建议镀金**：禁止建议模块 README 未声明的功能/灵活性（"不声明就不做"）。
3. **过程态出境**：评审记录出境（去向交工作流，不由本教条声明），不入 README。

## 严重度与裁决
Critical（bug / 数据丢失 / 静默失败）/ Important（错误处理、可维护性硬伤）/ Minor（风格、优化）。每条带 `file:line` + 错在哪 + 为何要紧 + 怎么修。末尾给明确裁决：**可收尾 / 需修后收尾**，不含糊。

## 发现处置（controller 侧，吸收自 receiving-code-review）
评审结果回到 controller 后，逐条走**复核 → 三岔 → 实施**：
1. **复核先于动手**：每条发现先独立验证真伪（读代码取证 / 查调用方 / 最小复现）——评审者也会错，盲从与无视同罪。任何一条读不懂 → 先问清全部再动手（条目间可能相关，部分理解 = 错误实施）。
2. **三岔处置**：属实且是实现问题 → 满足它；属实但根在契约（该写没写 / 写错）→ 回踢上游补契约，不打代码补丁；不属实 → 以技术理由驳回并在评审记录留痕（引用代码 / 测试证据）。驳回后被证明错了 → 事实性更正即可，不辩解、不长篇道歉。
3. **实施序**：阻断级（崩溃 / 安全 / 数据）→ 简单修 → 复杂修；一次一条、逐条过测试，禁止批量改完一起跑。
4. **禁表演性同意**：不写"你说得对 / 好发现"，直接陈述技术判断或直接动手——代码本身就是回应。评审建议"补全 / 做完整"时先查实际用量：无人使用 → 按不镀金原则拒绝；确有真实用量 → 那是"该写没写"的契约缺口，走第 2 岔回踢补契约后再做，不直接实现。

## 再入规则（收尾链内改了行为时）

「满足它」一岔若**改动了行为**（不只是改写法），改完不得直接收尾——须重过两道：**全套测试**（含守护物）+ **implement 的契约合规门**（实现是否仍恰好 = 模块契约）。改动并入本轮改动范围，固化点随之推进。

- **不重跑 implement 整个内循环**：那是逐条红测试的循环，此处无红可验；要过的只有上述两道门。
- **判据**：改动是否可能改变任一输入下的可观察输出？是 → 改了行为，走本节；否 → 纯写法，直接收尾。存疑按"改了行为"计（宁严不宽）。
- **改动大到需新增测试才守得住 = 不是「满足它」**：那是契约缺口，走第 2 岔回踢 brainstorming 补契约，再由正规回路实施——不在收尾链里长出新功能。

本节只覆盖收尾链内的改动。`simplify` 的精简因行为不变，不适用本节（其豁免条款见该 skill 的「退出」节，此处不复述）。

## 退出
Critical、Important 已满足或已回踢上游 → **收尾链结束**，回到模块循环取下一个未完成模块（收口触发条件见 brainstorming 的「收口」节，此处不复述）。

**收敛阀**：同一发现回踢上游达阈值（默认 3 次）仍不收敛 → BLOCKED 升级给人，附回踢历史（过程态出境）。
